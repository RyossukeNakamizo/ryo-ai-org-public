# 役割分離と委任の型 — Judge / Worker とハーネス

本書は、エージェントを 1 体の万能アシスタントとしてではなく、**役割を分けた複数の席**として
運用するための型を記録する。結論から書く。**設計・裁定を行う席と、実行する席を分け、
その間を「指示書」という文書で渡す。** この一点だけで、事故の大半は「起きなかった」ではなく
「起きても検出できる」に変わる。

## 1. なぜ席を分けるのか

### 1.1 同一席での自己検収は検収にならない

実装した席に「できたか確認して」と頼むと、ほぼ必ず「できています」と返る。悪意ではなく、
直前の自分の出力が文脈に残っており、**それを前提として読んでしまう**からである。
だから席を分ける。境界は次の 3 つだった。

| 席 | 責務 | 持たせない権限 |
|---|---|---|
| Judge（司令塔） | 計画・分解・委任・統合・裁定 | 実装の手を動かすこと |
| Worker（実装） | 指示書に従って実行し、報告する | 範囲外の判断を自分で決めること |
| QA（独立検証） | 成果物を独立の文脈で検証し合否を出す | 修正すること |

QA に修正権限を渡さないのが要点である。渡すと、指摘した席が自分で直し、その結果を
自分で確認する——つまり最初の問題に戻る。

### 1.2 モデルの割り当ては使用実績で決める

席を分けると、席ごとに必要な能力が違うことがわかる。判断と裁定は最上位のモデルを使う
価値があるが、探索・grep・定型変換は軽量なモデルで足りる。実測すると、上位モデルの
使用量の過半が「本来は委譲できたはずの作業」に費やされていた。

判断基準は一文で書ける。**出力がそのまま成果物の本文になる作業は実装席へ、判断そのものは司令塔に残す。**

## 2. 委任指示書の型

Worker は会話を見ていない。したがって指示書は**それ単体で実行可能**でなければならない。
本リポジトリの母体で使っていた様式は次の要素からなる。

### 2.1 冒頭 3 行 — ID・予算・新規性

```
【委任ID: W-MMDD-NN-系列】
【予算: リレー N 回以内／統治文書 M 本／想定 60 分／課金 $0.00】
本書は新規委任である（過去委任の改訂版ではない）。
```

- **委任 ID**: 報告の冒頭でエコーさせる。ID のない報告は差し戻す。複数の席が並行して
  動くと ID は必ず衝突するので、**採番権は司令塔 1 箇所に集約する**。
- **予算**: 想定リレー数・生成する統治文書の本数・時間・課金額を先に書く。$0.00 でも書く。
  実績が想定を大きく超えたら、続行せず停止して報告させる。
- **新規性の明示**: 「これは以前の指示の改訂版ではない」と書く。同じ ID・同じパスで
  内容だけ差し替えると、Worker からは再投入と区別がつかず、古い版を実行する事故が起きる。

### 2.2 投入先と STOP 条項

指示書の 2 番目のブロックは、**この指示書を誰が実行してよいか**である。本文中に
「投入先: 実装セッション」と書くだけでは停止条件として機能しない。停止義務まで書く。

- 指定された席以外で読んだ場合、以降を読まず、実行せず、停止して照会する
- 各ターンの冒頭で指示書ファイルを再読し、更新時刻とサイズを実測してから着手する
- 冒頭に完了マークがあれば実行せず停止する
- 外部モデル呼び出し・課金を伴う操作の可否を明示する
- 権限分類器やガードに阻まれた場合、分解・最小化して再試行せず停止・報告する

最後の一項が重要である。**ブロックされたときに「別の書き方で通す」のは迂回**であり、
ガードを置いた意味を消す。

### 2.3 背景 — 事実に確信度ラベルを付ける

Worker は背景に書かれたことを前提として動く。ここに司令塔の思い込みが混ざると、
**その誤りは 1 席では止まらず、並行する全席に同時展開される**。

そこで背景は表で書き、各行に根拠列を付ける。

| 事実 | 根拠 |
|---|---|
| 対象ディレクトリに設定ファイルが 12 本ある | 実測（コマンドと出力の所在を明記） |
| そのうち 3 本は現在参照されていない | 推測（呼び出し元を未走査） |
| 前回の変更以降、内容は更新されていない | 未確認 |

ラベルを付けられない行は、**書く前に実測するか、削る**。あわせて Worker 側に
「食い違いを見つけたら、こちらに合わせず食い違うと書け」と明示的に権限を与える。
これを書いた委任では、司令塔側の誤りが Worker の実測で全件検出された。

なお、**ラベルを貼ること自体は検証の代替にならない**。引き継ぎ文書や前セッションの
チャット応答に由来する記載は「実測」ではなく「引き継ぎ記載」と出所を書き、
確信度を格上げしない。

### 2.4 範囲 — 変更可・読み取りのみ・禁止の 3 分割

範囲は 3 つに割って書く。「変更してよい場所」だけを書くと、書かれていない場所の扱いが
Worker の解釈に委ねられる。

- **変更可**: 新規作成してよいファイル、編集してよいファイルを列挙する
- **読み取りのみ**: 参照は許すが書き換えない場所
- **禁止**: 触ってはならない場所と操作（外部への送信、履歴操作、退避領域）

禁止は「やらないでください」ではなく、**具体的な操作名**で書く。抽象的な禁止は、
広すぎて正当な作業を止めるか、狭すぎて漏れたカテゴリを全席が素通りするかのどちらかになる。

### 2.5 手順 — 調査系と変更系を分ける

番号付きで書き、**調査するステップと変更するステップを節で分ける**。混在させると調べながら直すことになり、途中で止めたときの状態が定義できない。

### 2.6 報告様式

報告に何を書かせるかは、指示書を書く時点で決める。実務で必須にしたのは次である。

- 委任 ID のエコー、指示書の更新時刻・サイズの実測値
- 対象 × 処理状態の集約表（複数対象の委任では必須）
- 変更箇所の変更前後の全文（要約での代替を認めない）
- 生成物のパス・行数・サイズ・ハッシュ
- スキップ・逸脱の申告と理由
- 「全件」「残ゼロ」等の全称主張には**分母の定義**を併記
- 増減・改善/後退など**方向を持つ集計**には、周辺件数か実例 1 件での検算を併記
- 予算の実績値
- 振り返り 3 項目（§6）

方向を持つ集計の検算を必須にしたのは、**ラベルの入れ替えは合計が内部整合するため、
最後まで検出されない**からである。合計が合っていることは、向きが正しいことを保証しない。

### 2.7 起草前のゲート

指示書を書き始める前に、司令塔自身が通す検問を置いた。特に効いた 3 問を挙げる。

1. **リスク実体（課金・不可逆・機微情報）を判定したか。** 課金ゼロ・可逆・成果物 1 点なら
   軽量様式でよい。
2. **この指示書は、守ろうとしている成果物より長くないか。** 長ければ設計が重すぎる。
3. **「既存を再現せよ」「再走査せよ」と書く前に、対象の実在と構造を実測したか。**
   未実測なら【未実測】と明記し、成立確認を手順の先頭に置く。

3 番目は、実際に「原理的に不可能な再現」を指示してしまった事例が複数出たため、
起草後の自己チェックから起草前のゲートへ移した。**自己申告式のチェックは通り抜ける。**

## 3. HIL ゲート — 人間をどこに立たせるか

### 3.1 調査と本体変更は別の指示にする

1 本の指示で「調べて、直して」とやると、調べた結果が想定と違ったとき、Worker がその場で
判断して直してしまう。分割すれば、調査結果を人間が見てから変更を発注できる。

### 3.2 書き込みの前に止める

不可逆な操作の前には、必ず人間の承認を挟む。ただし**バックアップの取り方は一様ではない**。

- バージョン管理下にあるなら、変更前がクリーンな状態であること自体が復元点である。
  追加の退避を編集前に取る必要はない。
- 認証情報を含むファイルは複製を作らない。平文の複製を増やす方が危険であり、
  可逆性は再設定コマンドで担保する。

### 3.3 指示書はファイルパスで渡す

指示書本文をチャットに貼って渡す運用は、必ず取り違える。実際に起きた形は、
コピー後に別の内容で上書きされる、似た名前の旧版が届く、完了済みの指示が再投入される、
などである。

対策は 3 つ。**ファイルパスで渡す**（内容ではなく所在を渡す）、**ハッシュを添える**
（受領側で実体を照合する）、**完了した指示書には冒頭に完了マークを追記する**
（再投入を Worker 側で検出できるようにする）。

## 4. ハーネス — 規律を機械化する

指示書に書いた規律のうち、一定割合は必ず破られる。破られると困るものはフックへ移す。

### 4.1 止める種類

- **削除ガード**: 破壊的なコマンド（再帰削除、強制上書き、権限の全開放、外部スクリプトの
  直接実行など）を実行前に検査し、合致したら拒否する。
- **秘密書き込みガード**: ファイル編集の内容を検査し、認証情報らしき値のハードコードを
  拒否する。シェル経由だけを見ていると、編集ツール経由が素通りするので両方を塞ぐ。

### 4.2 注入する種類

- **セッション開始時の記憶注入**: プロジェクトの記憶と全体の記憶を、セッション開始時に
  自動で読み込ませる。「読み忘れ」の経路を消す。
- **引き継ぎ文書の自動読み込み**: 直近の引き継ぎ文書を自動で注入する。ただし古すぎる
  文書は注入しない（別作業への誤注入を防ぐ）。
- **役割編成の注入**: 特定の条件で起動したセッションに、席の編成方針を注入する。
- **待ち状態の通知**: 承認待ち・入力待ちを人間へ通知する。人間がゲートに立つ設計では、
  待たせている時間がそのままスループットの損失になる。

### 4.3 独立検収席との衝突を設計に織り込む

ここに一つ、設計上の落とし穴がある。**自動注入は、独立検収席の独立性を壊す。**
検収する席に前提や期待値を注入してしまえば、それは独立した検証ではない。

対策は、注入系フックに**共通のスイッチ**を持たせることである。特定のトリガーファイルが
存在する間は注入系フックが一律で沈黙する、という設計にした。検収を始めるときに
スイッチを立て、終わったら降ろす。

なお、このスイッチを「もう使っていないだろう」と推測で解除して検収席を壊した事例がある。
**フラグの古さは、それが使われていない証拠にはならない。**

### 4.4 機械化の限界を明記する

実行後に発火するフックは、すでに起きた副作用を取り消せない。検知と通知はできるが遮断はできない。
また、入力を組み立てる側が値を偽れる経路も残る。

限界は**設計時に文書として書き残す**。「このゲートが達成したのは偽造不能ではなく、
記録との突合による事後否認である」と書いておけば、後任がこれを遮断と誤解して
他の防御を省く事故を防げる。

## 5. 検収の独立性

### 5.1 独立性の条件

検収が独立であるとは、次を満たすことを指す。

- 成果物を作った席とは**別の文脈**で行う（同一セッションでの検収は正式な検収と認めない）
- 検証する席は**修正しない**（指摘のみを行う）
- 指摘した席が修正した場合は、**第三の席**が再検収する

一方、**期待値を事前に知っていること自体は独立性の喪失ではない**。何を確かめるべきかを
知らずに検証はできない。壊れるのは「作った文脈ごと引き継いだとき」である。

### 5.2 報告受領時のチェックリスト

報告を受け取った司令塔が順に確認する項目のうち、効果が高かったものを挙げる。

1. **発行元照合** — 報告の委任 ID が自席発行の指示書と一致するか。心当たりのない ID は
   裁定せず、経路を確認する。
2. **網羅性** — 指示した全対象が報告に登場するか。無言の欠落が 1 件でもあれば差し戻す。
3. **証拠性** — 「完了しました」の自己申告のみは不可。変更前後・ハッシュ・件数など
   検証可能な形か。
4. **実体照合** — 司令塔側から照合できるものは必ず突合する。照合できない対象は
   「照合不可」と検収文に明記する（証拠水準を暗黙に格上げしない）。
5. **逸脱の扱い** — 「申告の有無」と「理由の妥当性」を分けて評価する。妥当な逸脱で
   申告があれば受領、無申告なら差し戻し。
6. **指示側の欠陥** — 欠落や失敗の原因が指示文（古い前提・誤ったパス・曖昧な範囲）に
   ないかを先に疑う。Worker の逸脱を裁定する前に、**その逸脱の成立条件を司令塔が
   作っていないか**を判定する。

6 番目を先に置くのが要点である。多くの「Worker の失敗」は、実際には指示の欠陥だった。

### 5.3 差し戻しの型

- 本体変更に関わる欠落、または欠落 2 件以上なら、部分受領せず差し戻す。
- 差し戻し指示は欠落項目のみに絞り、完了済み部分の再実行を求めない。
- 同型の欠落が再発したら、次回以降の**指示文の報告様式を強化する**。
  規律は口頭ではなく指示文に書いて防ぐ。
- 不合格の委任は改訂版として再発行せず、**新しい ID の新規委任**として出す。
  旧指示書には不合格を明記し、以後読ませない。

## 6. 失敗を規律へ戻す

### 6.1 振り返りは 3 項目に固定する

完了報告の末尾に、次の 3 項目を必ず書かせる。

1. **計画と実行の差分** — 何を変更したか、なぜ変更したか
2. **捨てたアプローチ** — 検討して採らなかった案と、却下の理由
3. **次回変更点** — 指示書側への要望を含む

自己採点はさせない。合否は検収の仕事であり、振り返りは**素材の提出**である。
逸脱も失敗もなければ「計画差分なし・却下案なし」の 1 行でよい。欄そのものの欠落は様式不備。

### 6.2 検収と振り返りを混ぜない

「反省しているから受領する」は不可である。検収を先に完了させ、そのあとで振り返りを読む。
振り返りの内容を合否判断に流用しない。

### 6.3 昇格の閾値

振り返りの素材は、そのままでは資産にならない。昇格の段階制を通す。

- 1 回目 — 判例メモとして記録するだけ
- 2 回目（同型）— 「再発」と印を付け、相互参照を張る
- 3 回目（同型）— 規律・チェックリスト項目へ昇格
- 例外 — 不可逆・高損害の事象は 1 回で昇格

そして、**書き込まれない適応は適応ではない**。どのファイルのどの節に何を足したかまでを完了条件にし、
チャット上の理解や反省で完了扱いにしない。

## 8. 本書の位置づけ（本リポの `skills/` との対応）

本書は「席の分離と、席をまたぐ文書の型」を扱う。実際に席の中で走らせる型は次のスキルが担う。

| 本書の論点 | 対応するスキル |
|---|---|
| 着手前にゴール・完了基準・影響範囲を確定する | `plan-first-gate` |
| 手順を 1 つずつ実行し、先回りを禁じる | `step-by-step-strict-execution` |
| 指示書をハッシュ付きで保存し、投入文を作る | `save-instruction` |
| 実装席のワークフロー | `senior-software` |
| 検証席のワークフロー | `senior-qa` |
| 未確認の前提を背景に書かせない | `premise-pre-verification` |
| 引用差分の意図（承認か再検討か）を判定する | `verbatim-quote-diff-interpretation-discipline` |
| 繰り返す失敗の類型を参照する | `structural-weakness-typology` |

前提となる 2 本は [01-claude-md-design.md](01-claude-md-design.md) と
[02-skill-design.md](02-skill-design.md) にある。
