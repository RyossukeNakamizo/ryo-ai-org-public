# CLAUDE.md の設計 — 79 行に何を残すか

本書は、エージェントが毎回読む唯一の文書である CLAUDE.md をどう設計したかの記録である。
結論から書く。**CLAUDE.md は「人が管理する不変原則」だけを置く場所にし、それ以外はすべて
別の層へ逃がした。** 結果として本文は 79 行に収まり、原則を足しても増えにくい構造になった。

対象読者は、Claude Code などのエージェント環境で自分用のスキル群とハーネスを組もうとしている
技術者である。設定値そのものではなく、判断の分け方を書く。

## 1. 前提 — セッションは毎回白紙で始まる

### 1.1 唯一「必ず読まれる」文書という性質

エージェントとの対話は、セッションが変われば前回の合意を覚えていない。前のセッションで
「今後はこうして」と伝えた内容は、次のセッションには存在しない。この非対称性を埋めるために
用意されているのが CLAUDE.md であり、その最大の特徴は**内容の良し悪しに関わらず毎回読まれる**
ことにある。

この性質は両刃である。書けば必ず届くが、書いた分だけ毎回のコンテキストを消費する。しかも
消費されるのは、本来その作業のために使いたかった枠である。

### 1.2 だから起きること — 「効いた指示」の堆積

放っておくと CLAUDE.md は必ず肥大化する。失敗が起きるたびに一行足すのが最も手軽で、
かつ短期的には実際に効くからである。半年も運用すれば、次の 4 種類が混ざった数百行になる。

1. いつでも適用される原則（「事実の断定にはラベルを付す」）
2. いま進行中の案件の現況（「現在フェーズ 2、残タスクは 3 件」）
3. 特定の作業手順（「この形式の資料はこの順で作る」）
4. 過去の事故の再発防止メモ（「あのとき壊したので今後は確認する」）

このうち毎回読ませる価値があるのは 1 だけである。2 は翌週には嘘になり、3 は該当作業のときにしか
要らず、4 は件数が増えるほど「読んでいるが守られない」状態に近づく。

CLAUDE.md 設計の要点は、書き方の巧拙よりも**この 4 種類を分離して、1 以外を追い出せるかどうか**に
ある。文書設計の一般論としても、指示を長くするほど個々の指示の遵守率は下がると指摘されている
（HumanLayer, "Writing a good CLAUDE.md"。参考文献を参照）。

## 2. 設計方針 — 置き場を限定し、逃がし先を先に作る

### 2.1 CLAUDE.md に入れるもの

判定基準は一つだけにした。**「案件が変わっても、半年経っても、そのまま真であり続けるか」。**
Yes なら本文、No なら別の層。具体的には次が残った。

- 応答の作法（言語、結論を先に置くこと、事実に確信度ラベルを付けること）
- 依頼されていない成果物を勝手に作らないこと
- 正本の置き場所の原則（開発物・業務文書・退避先をどこに置くか）
- 機密の扱い（認証情報を読まない・書かない・表示しない）
- 役割分担とモデルの割り当て方針
- 重大判断の型（絶対制約の遵守、課金前の見積り提示）
- 各種詳細規律への**ポインタ 1 行**

### 2.2 入れないもの

- **現況スナップショット**（進捗・残件・数値）。翌日には古くなる。
- **プロジェクト固有の手順**。該当プロジェクトの設定ファイルかスキルに置く。
- **同じ内容の二重定義**。ある規律の正本はどこか一箇所に決め、他はポインタで参照する。
- **注意書きで守らせようとしているもの**。守られない前提で機械化する（§5）。

このうち最後の二つは、後から効いてきた。二重定義を許すと、片方だけ改訂されたときに
「どちらが正か」を人間が毎回裁定する羽目になる。

### 2.3 逃がし先を 3 経路用意する

CLAUDE.md を短く保つには、削るだけでなく**受け皿**が要る。

| 逃がすもの | 逃がし先 | 理由 |
|---|---|---|
| 特定作業の手順・判断基準 | スキル（`SKILL.md`） | 該当作業のときだけ読み込まれる |
| 「注意しても守られない」規律 | ハーネスのフック | 実行前に機械が止める |
| 現況・学習事実・引き継ぎ | メモリ層と引き継ぎ文書 | 更新頻度が本文と違う |

受け皿を作らずに本文だけ削ると、削った規律が本当に消える。順序は「逃がし先を作る」→
「本文から移す」であって、逆ではない。

## 3. 実際の章構成 — 79 行の内訳

本リポジトリの母体となった環境の CLAUDE.md は、見出しを含めて 79 行である。内訳は次のとおり。

| 章 | 役割 | 本文行数 |
|---|---|---|
| (A) 共通規律 | 言語・結論先出し・確信度ラベル・依頼外成果物の禁止など | 9 |
| 正本パス | 開発物／業務文書／退避先の配置原則 | 5 |
| 命名規則 | 別ファイルへのポインタのみ | 2 |
| Git | コミット規約と、外部への送信可否 | 4 |
| 機密 | 認証情報と個人情報の扱い（表示を含む） | 3 |
| (B) チーム編成とモデル采配 | 席の定義と委譲先の判断基準 | 23 |
| (C) 詳細規律へのポインタ | 各正本への参照 3 本 | 4 |
| メモリ層の住み分け | どの情報をどの層に書くか | 3 |
| ツール障害時の規律 | 失敗したときに何をしないか | 3 |
| 絶対制約の遵守 | 「〜するな」を試行自体の禁止と読む | 6 |
| 課金実行の規律 | 見積りと合意の前置 | 4 |

三点だけ補足する。

**最大の章が「チーム編成」であること。** 23 行と突出しているが、これは表 1 枚で
「どの作業をどの席に渡すか」を決めており、ここが曖昧だと以降の判断がすべて揺れるためである。
分量の配分は重要度ではなく、**曖昧なまま運用したときの被害の大きさ**で決めた。

**「命名規則」が 2 行しかないこと。** 実体は別ファイルにあり、本文はポインタである。
段階的開示の最小形がこれで、規則そのものは詳細でよく、毎回読ませる必要がない。

**再発防止メモが「規律」の形でしか入っていないこと。** 個別の事故記録は本文に置かず、
一般化された判断ルールに昇格したものだけが章になる。昇格の閾値は §6 に書く。

## 4. 段階的開示をスキル群で実装する

### 4.1 ポインタ 1 行とスキル本体

CLAUDE.md 本文に「詳細は当該スキルを参照」と 1 行だけ書き、実体はスキル側に置く。
エージェントは常時 2 行分のコストしか払わず、必要な局面でだけ本体を読む。

スキル側に置くべきは、次のような「特定の局面でだけ必要な密度の高い判断基準」である。

- 発火条件と発火してはいけない条件
- 手順の分岐と、分岐ごとの出力様式
- 過去の判例（同型の失敗が何回起きたか）

### 4.2 二重定義の禁止

段階的開示を入れると、必ず「本文にも書いておいた方が安全では」という力が働く。これを許すと
本文が元の木阿弥になるうえ、改訂時に不整合が生まれる。そこで運用規則を一つ置いた。

> ある規律の正本は一箇所に決める。他の文書はポインタで参照し、内容を転記しない。
> 本文とスキルが矛盾した場合は、あらかじめ決めた側を正とする。

この「矛盾したときにどちらが勝つか」を先に決めておくのが要点である。矛盾の発生自体は
避けられないので、発生時の裁定コストをゼロにする方を選んだ。

## 5. 指示を増やさずに規律を守らせる — フックによる機械化

### 5.1 「注意書き」が効かない領域がある

運用してみると、規律には二種類あることがわかる。文章で伝えれば守られるものと、
何度書いても一定の確率で破られるものである。後者の典型は次のようなものだった。

- 破壊的なシェルコマンド（再帰削除、強制上書き）
- 認証情報の値がファイルやログに出ること
- セッション開始時に必要な前提を読み込ませること

これらは注意力の問題ではなく、**「うっかり通る経路が存在する」という構造の問題**である。
本文に一行足しても、経路は塞がらない。

### 5.2 フックが担う 3 種類の仕事

エージェント環境のフック機構は、ツール実行の前後やセッション開始などのタイミングで
任意のスクリプトを差し込める。ここに置いたのは次の 3 種類である。

1. **止める** — 実行前に内容を検査し、危険なコマンドや認証情報の書き込みを拒否する。
   合致したら実行させない。文書の注意書きと違い、通過率が原理的にゼロになる。
2. **注入する** — セッション開始時に、記憶や引き継ぎ文書を自動で読み込ませる。
   「読むのを忘れる」経路を消す。
3. **知らせる** — 承認待ちなどの状態を人間に通知する。人間がゲートに立っている設計では、
   人間を待たせないこと自体が性能になる。

この 3 分類は、そのまま「CLAUDE.md に書くべきか、フックにすべきか」の判定にも使える。
**止められるものは止める。止められないものだけ文章にする。**

### 5.3 機械化の限界を書いておく

フックは万能ではない。実行後に発火する種類のフックは、すでに起きた副作用を取り消せない
（検知と通知はできるが遮断はできない）。また、入力を組み立てる側が値を偽れる経路が
残ることもある。

重要なのは、**限界を設計時に文書化しておくこと**である。「このフックは遮断ではなく事後否認を
可能にするところまでを達成している」と書いておけば、後任者がそれを遮断だと誤解して
別の防御を省く事故を防げる。

## 6. 増やすときの規律 — 昇格閾値と棚卸し

短く保つ設計は、放置すれば必ず崩れる。崩れ方は一つ、**失敗のたびに規律が 1 行増える**である。
そこで増やし方そのものに規律を置いた。

- **1 回目は記録だけ**。判例メモとして残し、ルール化しない。
- **2 回目で「再発」と印を付ける**。まだルール化しない。
- **3 回目で規律・チェックリスト項目へ昇格させる**。ここで初めて構造の欠陥と認定する。
- **例外**: 不可逆・高損害の事象（データ事故、信用毀損、法規制）は 1 回で昇格させる。
- **定期的に棚卸しする**。一度も発火していない規律は廃止候補として洗い出す。

3 回という閾値は、個人のミスと構造の欠陥を分ける目安として採った。1 回で規律化すると、
たまたま起きた事象のために全員が恒久的なコストを払うことになる。

さらに一つ、実務で最も効いた運用がある。**新しい規律を足すときは、古い規律を一つ落とせないかを
必ず検討する**（one-in-one-out）。総量が増え続ける設計は、いずれ「全部書いてあるが誰も守れない」に
着地する。

## 8. 本書の位置づけ（本リポの `skills/` との対応）

本書は「毎回読まれる層をどう薄くするか」を扱う。逃がした先の設計は次のスキルが担う。

| 本書の論点 | 対応するスキル |
|---|---|
| 着手前にゴールと完了基準を確定させる | `plan-first-gate` |
| 記憶層に何を書き、何を書かないか | `memory-discipline` / `memory-gc` / `memory-pull` / `memory-push` |
| 未確認の前提を断定として書かせない | `premise-pre-verification` |
| 自分の判断の盲点を先に列挙する | `preemptive-challenger` |
| スキル自体の品質を定量評価する | `review-agent-essence` |
