# スキルの設計と運用 — 粒度・発火条件・増やし方

本書は、CLAUDE.md から逃がした規律とメソッドを「スキル」としてどう切り、どう運用したかの記録である。
結論から書く。**スキルの品質を決めるのは本文ではなく `description` である。** 本文がどれほど
精緻でも、発火すべき局面で発火せず、発火すべきでない局面で発火するなら価値はゼロになる。

## 1. スキルとは何を担う単位か

スキルは、特定の局面でだけ読み込まれる手順書である。CLAUDE.md が「毎回読まれる薄い層」なら、
スキルは「必要なときだけ読まれる厚い層」にあたる。したがって次の性質を持つものが向く。

- 発火する局面が言語で特定できる（「この種の依頼が来たとき」と書ける）
- その局面では詳細な判断基準が要る（薄く書くと役に立たない）
- 局面外では読まれなくてよい（常時適用の原則ではない）

逆に、**常に適用される原則をスキルにしてはいけない**。発火しない可能性が生まれるからである。
「必ず守ること」は CLAUDE.md かフックに置く。

## 2. 粒度 — 単一責務で切る

### 2.1 判定は「発火条件が一文で書けるか」

責務が複数あるスキルは、発火条件も複数になる。すると `description` が長くなり、
どの条件で読み込まれたのかが曖昧になり、本文のどの分岐を使えばよいかが決まらない。

実務での判定はこうした。**発火条件を一文で書けなければ分割する。**
「A のときと B のときに使う」と書きたくなったら、それは 2 本である。

### 2.2 分割したものは相互参照でつなぐ

分割すると、当然ながら連携が要る。本リポジトリのスキルには、末尾に「接続」節を置き、
前工程・後工程・正本の所在を明示しているものが多い。たとえば「見た目を決める」スキルの
後工程として「作り方を決める」スキルがある、という関係を本文に書いておく。

この相互参照は、**重複を検出する装置**でもある。新しいスキルを作るとき、既存スキルの接続節を
たどって同じ責務がないかを確認する。あれば新規作成ではなく既存の拡張を選ぶ。

## 3. `description` の 3 点構成

本リポジトリのスキルは、`description` を次の 3 点で書いている。

### 3.1 トリガー — いつ発火するか

「この語が来たら」「この操作の直前に」という形で、**観測可能な条件**を書く。
「必要なときに」のような書き方は発火条件として機能しない。

書き方は 2 系統ある。

- **明示コマンド型**: `/コマンド名` が投入されたときのみ発火する。
- **局面検出型**: 特定の依頼・特定の操作の直前に自動で適用する。

### 3.2 発火制限 — いつ発火してはいけないか

これがないスキルは、必ず過剰発火する。書くべきは次の 2 種類である。

- **適用除外**: 似ているが対象外の局面（「読み取りのみの操作では発火しない」）
- **自動発火の可否**: 既定は「提案までにとどめ、実行は人間の指示を待つ」

後者を既定にした理由は明快で、**発火権を人間に残すため**である。エージェントが良かれと思って
規律スキルを自動発火させると、人間が求めていない重い手続きが勝手に始まる。提案にとどめれば、
人間は一言で起動でき、不要なら無視できる。

### 3.3 キーワード — 検索で引っかかるための語

同義語・口語・英語表記を並べる。ここは網羅性が価値であり、文章の美しさは要らない。

### 3.4 3 点構成の効き方

この 3 点は、**過小発火（トリガー不足）と過剰発火（制限不足）を別々に潰す**ための分業である。
片方だけ書いたスキルは、必ずどちらかの方向に外れる。

## 4. 登録簿と運用手順（SOP）

スキルが 20 本を超えると、本文の品質とは別の問題が出る。**どこに実体があり、どれが最新か**が
わからなくなる問題である。これに対しては次の 2 つを置いた。

- **登録簿**: 全スキルの一覧と、それぞれの所在・系統・更新状態を持つ台帳。
- **運用手順（SOP）**: スキルを新設・改訂したときに、どこへ反映し、どの環境へ再配布するかの手順。

登録簿が答えるのは「このスキルの正本はどこか」「改訂したら他にどこを直す必要があるか」であり、
**内容の正しさではなく所在と同期状態を管理する**。内容の品質は別のスキル（レビュー用スキル）が
担当する。この分離をしないと、台帳が巨大な二重定義になる。

## 5. 二系統管理 — チャット側とエージェント側

同じ人物が、対話型のチャットとコマンドライン型のエージェントの両方を使う場合、スキルの
置き場は 2 系統になる。ここで最も多い事故が、**同じスキルを両系統に複製して片方だけ改訂する**
ことである。

採った方針は次のとおり。

1. **各スキルの所属系統を先に決める。** チャットの応答生成にしか関係しない規律は
   チャット側にのみ置き、エージェント側には複製しない。
2. **両系統で要るものは、正本を片方に決めて他方は差分だけ持つ。** たとえば様式の定義は
   一方に置き、他方には「その系統に固有の追加分」だけを書く。
3. **系統の境界判定そのものを規律にする。** 「これはどちらの系統の仕事か」を判定する
   スキルを 1 本置き、迷ったらそれを読む。

本リポジトリでは公開にあたって両系統のスキルを `skills/` に統一して配置しているが、
元の運用では上記の分離があった。取り込む際は、自分の環境の系統構成に合わせて再配置してほしい。

## 6. 増やし方の規律 — 判例メモから昇格させる

### 6.1 昇格の 3 段階

スキルの本文は、失敗のたびに増える。増やし方に規律を置かないと、数年で誰も読まない
チェックリストになる。採ったのは次の段階制である。

| 発生回数 | 扱い |
|---|---|
| 1 回目 | 判例メモとして記録するだけ。ルール化しない |
| 2 回目（同型） | 判例に「再発」と印を付け、関連箇所から相互参照する |
| 3 回目（同型） | 規律・チェックリスト項目へ昇格させる |
| 例外 | 不可逆・高損害（データ事故・信用毀損・法規制）は 1 回で昇格 |

3 回を閾値にしたのは、**個人の失敗と構造の欠陥を分けるため**である。1 回で規律化すると、
偶発的な事象のために恒久的なコストを全員が払う。

### 6.2 昇格させたら、どこへ書くかを決める

「学んだ」で終わらせないために、事象の性質ごとに書き込み先を決めておく。

- 特定作業でのエージェントの誤り → 該当スキルの**禁止事項**に 1 行追加
- 系統・環境の取り違え → 境界判定スキルの事例集
- 判断そのものの誤り → 判断構造スキルの判例

**書き込まれない適応は適応ではない。** 振り返りの文章を書いた時点では、まだ何も変わっていない。

### 6.3 one-in-one-out と棚卸し

新しい規律を足すときは、古い規律を 1 本落とせないかを必ず検討する。あわせて、定期的に
「一度も発火していない規律」を洗い出し、廃止候補として提案する。

この 2 つがないと、規律の総量は単調増加する。総量が増えると 1 本あたりの遵守率が下がるため、
**規律を足すこと自体が既存の規律を弱める**という逆説が起きる。

### 6.4 プロセスの重さはリスクに比例させる

最後に、最も高くついた教訓を書く。**手続きの重さは、対象のリスク実体（課金・不可逆性・
機微情報）に比例させる。** 可逆で費用ゼロの小さな修正にフル装備の手続きを適用すると、
本体 30 分の作業が数時間に膨らむ。メタ作業が本体を超え始めたら、それは規律ではなく渋滞である。

## 7. 収録 25 本の分類

本リポジトリのスキル 25 本は、機能で 3 群に分かれる。

### 7.1 規律系（9 本）— 何をしてはいけないかを定める

出力の前に自分を検問させる型。単独では成果物を作らない。

| スキル | 担う検問 |
|---|---|
| `premise-pre-verification` | 未確認の前提を断定として応答に埋め込ませない |
| `structural-weakness-typology` | 繰り返し発生する構造的弱点の類型カタログを参照させる |
| `step-by-step-strict-execution` | 複数手順を 1 つずつ実行させ、先回りの提示を禁じる |
| `verbatim-quote-diff-interpretation-discipline` | 引用に差分を含む返答の意図（承認か再検討か）を判定する |
| `plan-first-gate` | 非自明なタスクの着手前にゴールと完了基準を確定させる |
| `memory-discipline` | 記憶層に書くべき情報かを 3 問で判定する |
| `notion-io-discipline` | 外部ツールへの書き込み時の保存先・命名・更新規律 |
| `preemptive-challenger` | 結論を出す前に自分の判断への反論を列挙させる |
| `explanation-bridge` | 省略された思考の中間を補い、第三者に通じる順序へ直す |

### 7.2 メソッド系（10 本）— 成果物を作る型

| スキル | 出力 |
|---|---|
| `senior-software` | 設計・実装・リファクタの一貫ワークフロー |
| `senior-qa` | レビューとデバッグを 1 パスで行う品質ワークフロー |
| `web-app-architecture` | 要件からの構成選定（常に 2 案比較） |
| `frontend-mockup` | 自然言語・手書きメモから動くモックアップ |
| `aws-multicloud-mentor` | 既知クラウドからの対訳による学習・設計支援 |
| `gcp-multicloud-mentor` | 同上（別クラウド） |
| `graph-de` | 操作できるインタラクティブなチャート |
| `eli5-visual-explainer-v1` | 前提知識ゼロの読者向けの 1 枚図解 |
| `structured-doc-frontmatter` | 統一様式のプロジェクト文書 |
| `jikai-reflection` | 節目の内省を促す対話 |

### 7.3 運用系（6 本）— 資産と環境を保つ

| スキル | 担う運用 |
|---|---|
| `memory-gc` | 肥大化した記憶の圧縮・整理 |
| `memory-pull` | 全体の知識を個別プロジェクトへ取り込む |
| `memory-push` | 個別の学びを全体の知識へ昇格させる |
| `save-instruction` | 委任指示書の保存とハッシュ提示を 1 コマンド化 |
| `feedback-loop` | 定期巡回のトリアージを 1 語で起動 |
| `review-agent-essence` | スキル自体を 5 軸で定量評価し改善案を出す |

### 7.4 分類から見える偏り

規律系が 9 本と多いのは、**メソッドよりも「やらせない」ことの方が資産になりやすかった**
ためである。良い手順は状況が変われば陳腐化するが、失敗の型は繰り返す。

## 9. 本書の位置づけ（本リポの `skills/` との対応）

本書は「スキルという単位をどう切るか」を扱う。個々のスキルの中身は各 `SKILL.md` にある。
本書の論点を自分で運用するときに直接使えるのは次の 2 本である。

- `review-agent-essence` — 既存スキルの `description` と本文を 5 軸で評価する。§3 の
  3 点構成が満たされているかの点検に使える。
- `preemptive-challenger` — 新設しようとしているスキルが本当に必要か、既存の拡張で
  足りないかを、作る前に検問する。

前提となる層の設計は [01-claude-md-design.md](01-claude-md-design.md) に、
スキルを実際に人へ渡して動かす仕組みは [03-judge-worker-harness.md](03-judge-worker-harness.md) にある。
