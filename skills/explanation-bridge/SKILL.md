# explanation-bridge

## 目的
ユーザーの思考アルゴリズム（現象→抽象化→変数→モデル化→フレームワーク化）は資産。
弱点は出力時の中間省略のみ。本スキルは出力側だけを補正する。

## Step 0：ゴール固定性チェック
説明を組む前に必ず確認する。
- このゴールは固定か、変数か？
- 変数なら、ゴール候補を先に提示する（ユーザーは問題設定そのものを設計するタイプであり、
  受け手がゴールを所与と思い込んでいるズレが最大の事故源）。

## 受け手変数の推定（説明生成前に必須）
| 変数 | 問い |
|---|---|
| Goal | 受け手はこの説明から何を得たい/決めたいか |
| Knowledge | 受け手の前提知識レベル（ドメイン/技術） |
| Context | 受け手が既に知っている経緯はどこまでか |
| Depth | 受け手が必要とする詳細度（結論のみ/根拠まで/実装まで） |

不明な変数は推測で埋めず、ユーザーに1問だけ確認するか【推定】ラベルを付す。

## 説明の固定順序
1. 前提（「私の前提は○○です」から始める）
2. ゴール
3. 判断基準
4. 結論
5. 詳細

ユーザーの原文が「現象→結論」型だった場合、省略された2〜3（ゴール・判断基準）を
復元して挿入するのが本スキルの主作業。

## fidp-thinking との連携
- FIDP＝中身の構造（Fact/Insight/Decision/Proposal）
- 本スキル＝受け手較正（順序・粒度・前提共有）
- 第三者向けFIDP出力は、本スキルの受け手変数を通してから出す。

## 禁止事項
- ユーザーの思考プロセス自体の矯正を提案しない（補完であって矯正ではない）
- 受け手プロファイルの断定（〈担当者〉等の個別プロファイルは persona-* スキル側の管轄）

## 運用メモ
- 型化根拠はサンプル2件（2026-07-14の一〈担当者〉との会話）。
  トリガー範囲（常時自動適用）は初回運用1ヶ月後に見直す。
- fidp-thinkingとの二重構造化（冗長化）が実運用で発生した場合、
  fidp-thinking v2への統合を検討する。
