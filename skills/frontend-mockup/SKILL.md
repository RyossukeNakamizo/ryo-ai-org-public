# frontend-mockup v1.0（フロントエンド・モックアップ席)

手書きメモ・自然言語 → 動く画面。AI組織のデザイン/フロント席。

## 技術スタック方針（ユーザー定義の言語区分に準拠）

| 区分 | 言語 | 本スキルでの使い所 |
|------|------|------------------|
| コア | HTML / CSS / JavaScript | **モックの既定**。単一ファイル自己完結・ブラウザで即開ける・共有が最easy |
| 拡張 | TypeScript / JSX・TSX | **本実装移行時**。状態管理が複雑なモック（タブ・フォーム多段等）はReact(JSX)で |
| AltJS | CoffeeScript等 | 新規では使わない（保守案件で読む時のみ） |
| 周辺 | PHP | WordPress案件のテンプレート生成時のみ |

出力先の使い分け：単純な画面→単一HTML（Skillフォルダに保存しブラウザで開く）／
複雑なマルチコンポーネント（状態管理・ルーティング）→ web-artifacts-builder スキルに委譲。

## ワークフロー（4ステップ・イテレーション前提）

### Step 1：入力の解釈
- **手書きメモ・画像**：レイアウト要素を読み取り、**解釈を言語化してから作る**：
  「上部にヘッダー＋ロゴ左・ナビ右／中央にヒーロー（見出し＋CTAボタン）／
  3カラムのカード…と読み取りました。判読できなかった箇所：【推測】◯◯」
- **自然言語**：画面の目的（誰が何をする画面か）を1文で復唱。曖昧なら作りながら
  仮置きし、確認リストに回す（質問で止まらない——動くものが最良の質問）

### Step 2：デザイントークンの確認（最大3問・即答不要）
1. トーン（コーポレート堅め／モダン／ポップ 等）
2. ブランド色（指定色 or 参考にしたい既存物）
3. 想定デバイス（デスクトップ中心／モバイル中心／両方）
未回答のまま初版を出してよい（既定：モダン・ニュートラル配色・レスポンシブ両対応）。
初版に選択肢を見せる方が速い——**デザインの好みは「未知の既知」、見れば分かる**。

### Step 3：初版生成（品質基準）
- セマンティックHTML（header/nav/main/section/footer）＋CSS変数でテーマ一元管理
  （色変更の往復を1変数で済ませる）
- レスポンシブ既定（モバイル1カラム折返し）
- ダミーデータ規約：人名は「山田太郎」等の明示的ダミー、数値はキリの悪い架空値
  （実在と誤認されない）、画像はプレースホルダ（CSSグラデーション or 図形）
- アクセシビリティ最低限：コントラスト・alt・フォーカス可視
- **末尾に必ず「確認リスト」を添える**：【推測】箇所／トーンの選択肢／次の往復で
  決めたいこと3点以内

### Step 4：往復修正
- 修正指示は口頭で雑でよい（「もっと詰めて」「色が重い」）——解釈して1変数ずつ反映
- 3往復で収束しない場合は方向性が未確定のサイン→トーン違い2案を並べて選ばせる
  （ブレスト＆プロトタイプ：言葉で議論するより2案見せる）

## 本実装への橋渡し（求められた時のみ）
- モック確定後：コンポーネント分割案・TS化・フレームワーク選定（React/Next等）を
  要件（SEO・認証・データ量）から提案
- WordPress案件：確定モック→PHPテンプレート化の手順を提示
- 実装はClaude Code（Worker）へ委任可能な指示書形式で出せる（worker-delegation-protocol準拠）

## 禁止事項
1. 実在ブランド・他社サイトの複製（トーン参考と模倣の線引きを守る）
2. モックへの実データ・実名・機密情報の埋め込み
3. 確認リストなしの初版納品（【推測】の不可視化はイテレーションを壊す）
4. 要望にない機能の追加（kitchen sink禁止——モックは「見せて決める」ための最小物）

## 接続

- **web-artifacts-builder**：複雑なReact/マルチコンポーネント構築の委譲先

- **makora-adaptation**：デザイン往復で判明した好み（「ユーザーは余白広め・角丸小さめ」等）は
  本スキルの既定値として判例化——往復回数が使うほど減っていく
