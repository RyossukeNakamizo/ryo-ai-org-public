# structured-doc-frontmatter (v1.0)

A workspace-global skill for generating project documents with a unified frontmatter + 8-section structure. Designed to maximize claude-mem semantic search precision across projects.

## Why this skill exists

claude-mem operates as a semantic index layer across the entire Claude workspace (all projects). Its retrieval precision depends on document frontmatter consistency — a unified schema gives the semantic index stable, comparable metadata fields across projects, which improves retrieval precision. (注: 旧版に記載していた Shao et al. 2024 EMNLP の定量引用は実在を確認できなかったため削除。)

This skill enforces that schema for **all non-handoff project documents** generated in the workspace. handoff YAMLs (single-session continuity, time-axis) go through `context-handoff` skill; this skill covers everything else (content-axis, multi-session reusable artifacts).

## Scope boundary vs context-handoff

| Skill | Axis | Output format | Use case |
|-------|------|---------------|----------|
| `context-handoff` | Time (session continuity) | YAML | Resuming a specific in-flight task in a fresh session |
| `structured-doc-frontmatter` (this) | Content (knowledge artifact) | Markdown with YAML frontmatter | Phase snapshots, session summaries, ADR records, PoC backlogs, stage-1/2 drafts, reusable pattern catalogs |

**Mutual exclusivity rule**: if the document's primary purpose is "let a fresh Claude session resume work", use `context-handoff`. Otherwise use this skill.

## Canonical template

Every document generated by this skill MUST start with this frontmatter block, in this exact field order:

```yaml
---
project: <project name with optional client/contract context>
industry: <industry vertical, e.g., 生命保険, 製造業, 金融>
use_case: <specific use case, not a generic category>
type: <document type, e.g., Phase 6(b) backlog, Session 60 closure, ADR D3, Stage 2 design draft>
status: <current state, e.g., 段階1 起草中, 段階2 確定済, レビュー待ち, deprecated>
reusable_score: <integer 1-10, or "未評価"; estimate of cross-project transferability>
last_updated: <YYYY-MM-DD HH:MM JST>
---
```

Followed by exactly these 8 H1 sections, in this order:

```markdown
# Goal
# Context
# Decisions
# Architecture
# Evaluation
# Failure
# Reusable Pattern
# Next Action
```

## Field semantics

### Frontmatter

- **project**: snake_case or natural-language project identifier. Include client/contract context if relevant (e.g., `〈案件〉 Agentic AI PoC (〈案件〉受託 / batch-a)`). This is a primary claude-mem index key.
- **industry**: industry vertical at sufficient granularity for cross-project retrieval. Avoid overly broad terms ("テック") in favor of specific verticals ("生命保険", "工場 IoT", "サプライチェーン金融").
- **use_case**: the specific business problem, not a technology category. "要確認候補抽出 + レビュー支援ワークベンチ" is correct; "RAG 実装" is too generic.
- **type**: the document's role in the project lifecycle. Examples: `Phase 6(b) backlog (段階1)`, `Session 60 closure 整理`, `ADR D3 (Phase B/C skip recovery)`, `Stage 2 prototype design draft`, `5/7 Slack 報告骨格`, `Reusable Pattern catalog`.
- **status**: current state, time-aware. Use one of: `段階1 起草中`, `段階1 完了`, `段階2 起草中`, `段階2 確定済`, `レビュー待ち`, `ユーザー 承認済`, `commit 済`, `deprecated`, `superseded by <doc>`.
- **reusable_score**: integer 1-10 or `未評価`. Cross-project transferability estimate. 1-3 = project-specific, 4-6 = within-industry transferable, 7-10 = industry-agnostic. Defer to `未評価` in 段階1; commit a number in 段階2.
- **last_updated**: timestamp in `YYYY-MM-DD HH:MM JST` format. Update on every edit, even minor.

### 8 H1 sections

Each section has a defined purpose. Do not invent additional H1 sections — if content does not fit, evaluate whether the document type is correct (it may need to be a handoff YAML or an ADR-only entry in `docs/DECISIONS.md`).

- **# Goal**: single-paragraph statement of what this document accomplishes. Acceptance-criteria style preferred over narrative. NOT the project's overall goal — the document's specific goal.
- **# Context**: WHY this document exists now. What just happened, what constraint emerged, what stakeholder requested it. Sufficient context that a fresh Claude session can understand the document's reason-for-being without prior chat history.
- **# Decisions**: WHAT was already decided and WHY. Always pair decision with rationale. Use "確定済" / "未確定" subdivision when both coexist. Decisions made by stakeholders (ユーザー, 〈担当者〉, 〈担当者〉) should attribute who decided.
- **# Architecture**: technical/structural design relevant to this document. Reference external architecture documents rather than duplicating them. In stage-1 drafts, list candidates only; defer structuring to stage-2.
- **# Evaluation**: assessment criteria, current scores, gaps. Quantitative when possible (precision/recall, latency targets, cost ceilings); qualitative with explicit criteria when not. In stage-1, list criteria candidates only.
- **# Failure**: failure modes (occurred or anticipated), structured by type. In retrospective documents, attribute to canonical type catalogs (e.g., Memory #23 類型). In forward-looking documents, enumerate anticipated failure modes with likelihood × impact.
- **# Reusable Pattern**: cross-project transferable insights. Each pattern: 1-line summary + scope of applicability + reference to origin. This section drives `reusable_score`. In stage-1, list pattern candidates as references only; new pattern abstraction happens in stage-2.
- **# Next Action**: ordered or parallel next steps. Each step: who (ユーザー / Worker / Claude) × what × when × dependency. Stage-1 documents always include "stage-2 起草" as a Next Action.

## Memory #27 two-stage drafting integration

When the document is a Phase or Session artifact (not a real-time decision record), apply Memory #27 two-stage drafting:

### Stage 1 (immediate post-phase, cooling period before structuring)

- Each section: 1-2 lines summary + 系統タグ in `[系統: ...]` format at section end
- No new structured judgment (no priority matrix, no dependency graph, no implementation sketch)
- Frontmatter `status: 段階1 起草中` or `段階1 完了`
- Frontmatter `reusable_score: 未評価`
- `# Next Action` MUST include "5/X 以降に段階2 起草" or equivalent cooling deadline

### Stage 2 (after cooling period, structuring allowed)

- Each section: full structured content
- New ADR entries triggered as separate commits to `docs/DECISIONS.md`
- Frontmatter `status: 段階2 確定済`
- Frontmatter `reusable_score`: integer 1-10
- Stage 1 and Stage 2 are independent commits (audit trail separation per Memory #27)

## Filename convention

```
<type>_<project>_<YYYYMMDD>.md
```

Examples:
- `phase_b_stage1_myl_poc_20260504.md`
- `session_60_closure_myl_poc_20260501.md`
- `adr_d3_myl_poc_20260504.md`
- `stage2_design_hino_factory_20260420.md`

Do NOT use ambiguous names like `notes.md` or `current_state.md` — claude-mem semantic index degrades when filenames lack discriminating tokens.

## Save location

- **Project-specific docs**: under the project's `docs/` directory (e.g., `~/Documents/Claude-Workspace/myl-ai-agent-poc_batch-a/docs/`).
- **Cross-project reusable pattern catalogs**: under a dedicated workspace-global location (default: `~/Documents/Claude-Workspace/_shared/patterns/`).
- **Claude.ai-side generation**: save to `/mnt/user-data/outputs/` and present via `present_files`. The user moves the file to its final location.

## Anti-patterns

- **Sectional drift**: adding non-canonical H1 sections (e.g., `# Stakeholders`, `# Risks`). If the content is essential, fold it into one of the 8 canonical sections.
- **Frontmatter omission**: every document MUST have the full frontmatter block. Missing fields break claude-mem indexing.
- **Stage 1 / Stage 2 conflation**: writing structured judgment in a 段階1 document defeats the cooling-period purpose. If structuring is needed immediately, the document type is wrong (probably should be an ADR or a handoff YAML, not a phase snapshot).
- **Reusable_score inflation**: marking project-specific decisions as 8-10. The score is for cross-project transferability, not for "importance to this project".
- **Use as handoff substitute**: if the document's purpose is "next session resume", use `context-handoff` skill instead.

## Compatibility

- **Claude Code**: this skill is read by `~/.claude/skills/structured-doc-frontmatter/SKILL.md`. Auto-triggered when document creation matches description triggers.
- **Claude.ai**: this skill, when placed in user's skill directory, applies to fresh chats globally. Project-level skill (`/mnt/skills/user/` of a specific project) does NOT achieve workspace-global coverage.
- **claude-mem**: documents generated by this skill are first-class citizens in claude-mem's semantic index. The frontmatter unification is the precision-boost contract.
- **context-handoff skill**: complementary, mutually exclusive. See "Scope boundary" section.
- **Memory #27**: this skill operationalizes Memory #27's two-stage drafting principle for non-handoff documents.
