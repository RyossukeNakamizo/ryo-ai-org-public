# web-app-architecture v1.0（Webアプリ・アーキテクチャ選定席）

frontend-mockup（何を見せるか）→ **本スキル（どう作るか）** → Worker委任（作る）→ qa-acceptance（検収）。

## 選定プロセス（要件4問 → 2案比較）

### 要件4問（構成を左右する順）
1. **SEO・初期表示**：検索流入が要るか（要る→SSR/SSG系、不要→SPA可）
2. **認証・データ機密**：ログイン必須か、APIキー等の秘匿があるか（秘匿あり→BFF層が必要になる典型条件）
3. **データ鮮度と状態**：リアルタイム性・複雑な画面状態があるか
4. **作る人と運用**：誰が保守するか（ユーザー単独PoC／ジュニア込み／顧客引き渡し）——技術は運用者のスキルで選ぶ（判断木E思想）

|---|---|---|

## 構成パターン表（フロント/BFF×バックエンド×接続方式）

| フロント/BFF | バックエンド | 接続方式 | 向いている場面 |
|---|---|---|---|
| Next.js（React） | Node/NestJS または API Routes自体 | REST/GraphQL/tRPC | SEO要・BFF内蔵で層を減らしたい・Vercel系デプロイ |
| Nuxt（Vue） | Laravel/Rails/Go等 | REST/GraphQL | Vue資産・既存バックエンドが別言語 |
| SvelteKit | FastAPI/Django/Node等 | HTTP/JSON | 軽量・高速な中小規模アプリ |
| SPA単体（React/Vue） | 任意のAPIサーバ | ブラウザ直APIコール | 社内ツール・PoC・SEO不要（**最短経路**） |

**原則：バックエンド接続はHTTP/JSONのクライアント–サーバ通信パターンそのものであり、
特定フレームワーク固有機能ではない。**フレームワーク選定と接続方式選定は分離して考える。

### BFFを挟む/挟まない判定
- **挟む**：秘匿情報（APIキー・トークン）の隠蔽が要る／複数バックエンドの集約が要る／
  フロント都合のデータ整形が頻繁（バックエンドを汚したくない）
- **挟まない**：単一API・社内PoC・1画面アプリ——**1画面SPAにBFFは過剰設計**（kitchen sink検査）

## レンダリング戦略（Next系選定時）
| 戦略 | 選ぶ条件 |
|------|---------|
| SSG | 内容が固定（LP・ドキュメント）。最速・最安 |
| SSR | SEO要＋ユーザー毎に内容が変わる |
| CSR（SPA） | ログイン後ツール・ダッシュボード。SEO不要 |
| ISR/ハイブリッド | 上記混在。ページ単位で使い分け |

## 認証パターン（要件2で秘匿ありの場合）
- 社内/PoC：ID基盤に委譲（Entra ID／Cognito／Identity Platform——クラウドメンター3本と接続）
- BFF経由：トークンはBFFで保持しブラウザに出さない（httpOnly cookie）
- 原則：**認証を自作しない**（PoCでも）

## ユーザーの既定構成（迷ったらこれ・実案件実績ベース）
| 用途 | 構成 |
|------|------|
| RAG/AI PoCデモ | **SPA（React）＋ FastAPI ＋ Azure App Service**（RAG評価基盤・〈案件〉デモの実績構成。チャットUI→Agent API→LLM の3層） |
| 商材LP・ドキュメント | 静的HTML/SSG＋ホスティング（Static Web Apps／Cloud Run／Vercel系） |
| 顧客引き渡し前提 | 顧客の既存スタックに合わせる（要件4問の4を最優先。判断木E：運用者が読める技術） |
| マルチクラウド提案 | デプロイ先2案併記（App Service↔Cloud Run↔Lambda/Amplify——WF設計テンプレの2案併記原則） |

## 禁止事項
1. 単案提示（必ず2案比較＋要件からの導出）
2. 流行・個人の好みを選定根拠にすること（「今はみんな◯◯」は根拠ではない）
3. 要件にないBFF・マイクロサービス等の過剰設計（kitchen sink検査）
4. 認証の自作提案
5. フレームワークのバージョン・機能を検索確認なしで断定すること
